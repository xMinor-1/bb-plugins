# scripts

Служебные скрипты репозитория.

| Скрипт | Что делает |
| --- | --- |
| `new-plugin.sh` | Создаёт новый плагин и регистрирует его в `.bb/plugins.json`. |
| `check-after-bb-upgrade.sh` | Сторож: проверяет, не сломало ли обновление bb наши плагины — все из индекса и все, что стоят в bb. |
| `patch-taskboard-statuses.py` | Даёт GitHub-задачам в панели Taskboard три статуса вместо двух: Todo → In Progress → Done. |

## Сторож `check-after-bb-upgrade.sh`

### Зачем

После обновления bb любой плагин может перестать собираться или запускаться.
Хуже всего ломаются те, что встраиваются в интерфейс bb своим DOM: контент-скрипт
находит узел, который рисует сам хост, и кладёт в него своё. Держится это на
якорях хоста:

| Якорь | Кто использует | Зачем |
| --- | --- | --- |
| `[data-testid="plugin-sidebar-footer-action-<pluginId>-<actionId>"]` | `usage-meter`, `server-status`, `theme-toggle`, `sticker-note` | кнопка в футере сайдбара: кольца, значок «день/ночь», счётчик стикеров |
| `[data-testid="plugin-sidebar-footer-item-<pluginId>-<id>"]` | `sticker-note` | та же кнопка, когда bb рисует слот пунктом |
| `[data-radix-popper-content-wrapper]` | `usage-meter` | обёртка тултипов хоста: попап отодвигается, чтобы не налезть на подсказку |
| `[data-plugin-icon-asset]` | `theme-toggle` | значок кнопки из `branding.icon`, нарисованный маской: его плагин и перекрашивает |
| `button[aria-label^="Context window"]` | `context-compact` | кольцо контекста в композере, на него встаёт карточка сжатия |
| `[data-thread-window]` | `context-compact` | панель треда: по ней видно, чьё кольцо в разделённом окне |
| `img[src*="/assets/bb-logo-"]`, `<title>bb</title>`, `link[rel~="icon"]` | `app-branding`, `fleet-kit` | логотип, заголовок и значки вкладки, которые подменяет брендинг |

Значок-маску bb рисует, только если имя иконки в регистрации кнопки ему
неизвестно: с 0.46 встроенное имя (`"Palette"`) побеждает брендинг, а пустое
снимает кнопку вовсе. Поэтому у `theme-toggle` в регистрации стоит
`"theme-toggle/artwork"` — имя вне словаря bb.

testid кнопки футера хост собирает шаблоном из id плагина и id слота, поэтому в
собранном коде приложения лежит не готовая строка, а сам шаблон — сторож
проверяет именно его форму.

Опасность в том, что поломка тихая. Если обновление bb переименует или уберёт
якорь, плагин останется `running`, в логах будет пусто, а индикатор просто
исчезнет из интерфейса — и заметить это можно только глазами.

Контент-скрипты `bug-report-button` 0.1 и `model-usage` якорей хоста не ищут:
первый кладёт свою кнопку прямо в `document.body`, второй только обновляет данные
по таймеру. Новый плагин с контент-скриптом, которого нет ни в одном из этих
списков, сторож покажет вопросом — его якоря надо дописать.

### Что проверяет

Сравнивает версию запущенного bb (`~/.bb/bb-app-runtime.json`, поле `version`) с
последней проверенной (`.bb/last-checked-version`).

- Версия та же — молча выходит с кодом `0`. Гонять можно хоть ежедневно.
- Файла с версией нет — считает, что версия сменилась, и проверяет.
- Версия сменилась — печатает отчёт по-русски и проверяет четыре вещи:
  1. якоря хоста ещё есть в собранном коде приложения (грепом по
     `<bb>/node_modules/bb-app/app/dist/assets/*.js` и `index.html`, путь берётся
     из `entryPath` того же `bb-app-runtime.json`);
  2. `PLUGIN_ID`/`ACTION_ID` в `app.tsx` у `usage-meter`, `server-status` и
     `theme-toggle` совпадают с тем, как bb зовёт плагин (`package.json` →
     `name` без префикса `bb-plugin-`);
  3. каждый наш плагин собирается (`bb plugin build`) — из того каталога,
     откуда его запускает bb;
  4. каждый установленный плагин стоит в `running`, без `degraded` и без сервисов
     в `backoff` (`bb plugin list --json`); `stopped` у сервиса — норма: так
     выглядит разовый сервис, который отработал и вышел.

Какие плагины проверяются:

| Плагин | Сборка | Статус | Сбой держит версию |
| --- | --- | --- | --- |
| наш, стоит из этого репозитория | на месте, в `plugins/<имя>` | да | да |
| наш, стоит из git или из рабочего дерева агента | во временной копии, `node_modules` — ссылкой на установленный | да | да |
| наш, в индексе, но не стоит в bb | если есть `node_modules` | пропуск | да |
| выключен в bb | пропуск | пропуск | — |
| чужой, поставлен не из bb (`chime`, `taskboard` и т. п.) | нет | да, только вопросом | нет |
| встроенный в bb | нет | нет | — |

Наш — в `.bb/plugins.json`, поставлен по пути или из git этого репозитория
(`origin`). Ошибки в обработчиках у running-плагина — вопрос, а не сбой.

Коды возврата: `0` — всё цело, `1` — что-то сломано, `2` — сторож не смог
отработать (не запущен bb, нет `node`, не нашёлся каталог бандлов).

Сторож только читает и собирает: ничего не удаляет, не переустанавливает, не
коммитит и не пишет `.bb/last-checked-version` — версию записывает тот, кто
разобрал отчёт. Кэш git bb и чужие рабочие деревья он не трогает: их плагины
собираются во временной копии, которая удаляется на выходе. Полный прогон
занимает около 20 секунд.

### Запуск руками

```sh
cd "/home/coder/Work/3. projects/BB Plugins"
./scripts/check-after-bb-upgrade.sh; echo "код: $?"
```

Посмотреть полный отчёт на неизменившейся версии — подсунуть свой файл рантайма:

```sh
sed 's/"0.39.0"/"0.99.0"/' ~/.bb/bb-app-runtime.json > /tmp/rt.json
BB_APP_RUNTIME_JSON=/tmp/rt.json ./scripts/check-after-bb-upgrade.sh
```

Зафиксировать текущую версию как проверенную:

```sh
printf '%s\n' "$(sed -n 's/.*"version"[[:space:]]*:[[:space:]]*"\([^"]*\)".*/\1/p' ~/.bb/bb-app-runtime.json)" \
  > .bb/last-checked-version
```

## Автоматизация: ежедневный сторож

Сторожа дёргает автоматизация bb — агент, который не просто зовёт скрипт, а сам
чинит плагины, если тот ругнулся.

```text
Проект:      proj_58ezp634x9 (BB Plugins)
Автоматизация: auto_jbumkothkqy — «Сторож плагинов после обновления bb»
Расписание:  15 9 * * * (Europe/Sofia), раз в сутки
Агент:       claude-code / claude-opus-5-5[1m], доступ full
Каталог:     /home/coder/Work/3. projects/BB Plugins
```

Что делает агент:

- версия bb не менялась — скрипт молчит, агент сразу заканчивает: ничего не
  собирает, не переустанавливает, не коммитит;
- версия сменилась, всё цело — записывает новую версию в
  `.bb/last-checked-version` и коммитит один этот файл с пушем, чтобы завтра
  проверка снова была бесплатной;
- версия сменилась, что-то отвалилось — ищет новый вид якоря в собранном коде
  приложения и правит селекторы того плагина, которому он принадлежит; если
  плагин не собирается из-за непоставленных зависимостей — `npm install` в его
  каталоге. Дальше `npx tsc --noEmit`, `bb plugin build`, `bb plugin reload`,
  проверка `bb plugin list` и `bb plugin logs`, при необходимости обновляет самого
  сторожа, записывает версию и коммитит с пушем только свои файлы. Плагины,
  поставленные из git, правит только в репозитории: выпуск версии — за человеком;
- починить не вышло — не коммитит ничего и пишет, что сломалось.

### Управление

```sh
P=proj_58ezp634x9
A=auto_jbumkothkqy

bb automation show   $A --project $P          # настройки, промпт, следующий запуск
bb automation run    $A --project $P          # прогнать прямо сейчас
bb automation runs   $A --project $P --limit 5             # история запусков
bb automation runs   $A --project $P --limit 1 --output <runId>   # что ответил агент
bb automation pause  $A --project $P          # приостановить
bb automation resume $A --project $P          # снова включить
bb automation update $A --project $P --cron "0 8 * * *" --timezone Europe/Sofia
```

Автоматизация живёт в проекте `BB Plugins` (`proj_58ezp634x9`), а не в
`proj_personal`: `bb automation create` этот id не принимает — `Project not
found`.

## Патч `patch-taskboard-statuses.py`

### Зачем

`bb-plugin-taskboard` — чужой плагин из npm. У GitHub-задач он знает только два
состояния, Open и Closed, поэтому канбан получается из двух колонок. Патч правит
установленный плагин так, чтобы колонок стало три:

| Колонка | Что это на GitHub |
| --- | --- |
| Todo | открытая задача без меток-стадий |
| In Progress | открытая задача с любой меткой-стадией |
| Done | закрытая задача |

Метки-стадии — подстатусы внутри работы, колонка от них одна:

| Метка | Стадия |
| --- | --- |
| `coding` | пишется код |
| `review` | идёт проверка кода |
| `qa` | проверка результата |
| `blocked` | ждёт внешнего |
| `in progress` | в работе без уточнения стадии |

Перетаскивание карточки в In Progress вешает `coding`, обратно в Todo или в Done —
снимает все стадии и меняет состояние задачи. Стадия внутри работы меняется меткой
на GitHub или в панели GitHub-плагина. Набор стадий задан списком `IN_PROGRESS_LABELS`
в скрипте — если нужны другие, править там и переприменять патч.

Метки-стадии в панели покрашены в свои цвета — стадию видно с карточки, не открывая
задачу. Цвета и список меток — `LABEL_COLORS` в скрипте; патч добавляет каждой метке
атрибут `data-label` в `dist/app.js` и дописывает правила в `dist/app.css`. Стадийная
метка на карточке показывается первой: в канбане на карточку помещаются только две.

Метки нужно один раз завести в каждом репозитории:

```sh
for label in coding review qa blocked; do
  gh label create "$label" --repo <owner/repo> --force
done
```

### Как применять

```sh
python3 scripts/patch-taskboard-statuses.py
bb plugin reload taskboard
```

Скрипт идемпотентный, правит `dist/server.js` (его и исполняет bb) и
`sources/github.ts` в кэше npm, рядом кладёт бэкапы `*.tb-orig`. Откат —
`--revert`.

### Когда переприменять

Патч живёт в кэше npm и слетает при `bb plugin update taskboard` — после
обновления плагина прогнать скрипт заново. Если апстрим переписал GitHub-адаптер,
скрипт остановится с сообщением, какой фрагмент он не нашёл: значит, замены надо
переписать под новую версию плагина.
